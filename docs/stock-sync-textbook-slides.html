A field guide to distributed state

Offline stock sync

How two mobile devices record changes without a network, send them safely, and converge on the same group inventory.

The client

Stores a durable outbox and a group pull cursor.

The backend

Validates events and assigns one ordered sequence per group.

The sync loop

Pushes local events, then pulls the shared log in pages.

1 · Mental model

Sync events; don’t replace the whole inventory

A mobile action becomes an operation. The backend applies that operation to current stock and appends it to a group-wide log. The log is the shared history; on-hand quantities are the resulting state.

2 · Offline write

Save the operation before trying the network

One local transaction
  1. Create a unique opId.
  2. Assign this device’s next deviceSeq.
  3. Copy the current group cursor into baseSeq.
  4. Write the complete request to the durable outbox.
  5. Update the local view optimistically.
{
  "deviceId": "device-A",
  "deviceSeq": 8,
  "baseSeq": 5,
  "op": {
    "opId": "stable UUID for retries",
    "type": "receive",
    "productId": "ball",
    "storageId": "main",
    "quantity": 4
  }
}

The values above are illustrative. Persist the actual body and resend it unchanged after timeouts.

A queued event remains pending until the server acknowledges it. A temporary network failure must not generate a new opId.

3 · Sequence vocabulary

Several counters track different scopes

NameScopeMeaningExample in this lesson
deviceSeqOne deviceOrdinal of an operation submitted by that device.A=1, B=1
last_device_seqOne device, backendLast accepted device sequence; next expected is +1.0 → 1 on each device
baseSeqOne operationGroup cursor copied when the operation was created.A=0, B=0; immutable on retry

next_seqGroup counterNext group sequence the backend will allocate.1 → 2 → 3

Do not mix the scopes: deviceSeq is local to a device; seq and latestSeq are group-wide.

4 · Reconnect algorithm

Pull, push in order, then pull again

1 · Pre-pull

Refresh shared state

GET after the saved lastAppliedSeq. Apply pages in seq order and persist state with the new cursor.

2 · Push

Drain the outbox

POST one operation at a time in ascending deviceSeq. Remove only after acknowledgment.

3 · Post-pull

Catch concurrent writes

Pull again. This picks up operations from other devices that arrived during the push phase.

sync(group):
  pullUntilCaughtUp(group)
  for op in outbox ordered by deviceSeq:
    POST the exact saved request
    on success: remove from outbox
    on timeout: retry the exact same request
  pullUntilCaughtUp(group)
The push acknowledgment’s latestSeq helps decide whether another pull is useful. A new write can commit just after that value was sampled.
Use authenticated appId and groupId headers on both endpoints05

Retry rule: if the outcome is unknown after a timeout, resend the same opId, deviceSeq, and body. The server returns the original operation result instead of applying it twice.

6 · Backend transaction

One transaction orders writes for a group

  1. Authenticate the caller and verify group membership.
  2. Validate the operation and check whether opId was already accepted.
  3. Lock the group counter so concurrent operations get distinct ordered sequences.
  4. Check deviceSeq; lock affected stock positions.
  5. Apply the event to current on-hand, assign seq, and persist operation, snapshot, and device cursor.
  6. Commit, then return the operation’s seq and the sampled latestSeq.
Atomicity

The position update and operation log entry commit together. A failed transaction should leave neither half applied.

Serialization

The group counter is locked during the transaction, so two successful writes receive a definite order.

Current materialized stock is updated with the event log07

7 · Pull contract

Pull reads a bounded page from the group log

Request: GET /api/stock/ops?after=<lastAppliedSeq>

latestSeq = sample current group head
ops = SELECT ...
      WHERE seq > after AND seq <= latestSeq
      ORDER BY seq
      LIMIT 500
nextAfter = last returned seq (or after if empty)
hasMore = nextAfter < latestSeq
Lower bound

seq > after prevents replaying the cursor item.

Upper bound

seq <= latestSeq keeps the page aligned with its reported head.

Page size

At most 500 operations; apply them and continue from nextAfter if hasMore.

Persist inventory changes and the new cursor atomically. If the app crashes between those writes, it can skip or reapply operations.
latestSeq is a sampled head, not a live subscription08

9 · Recovery and conflicts

Retry transport failures; resolve semantic conflicts

Unknown network outcome

Retry the same operation

A timeout does not prove the server failed to commit. Reuse the original opId and body; idempotency prevents a double application.

Count conflict · HTTP 409

Refresh and make a new count

If current on-hand differs from a count line’s expected, the server rejects the count with conflict details. Pull, reconcile, then queue a revised operation with a new opId.

Sequence gap · HTTP 409

expectedDeviceSeq tells the client the next device operation number. Reconcile the outbox before sending more.

Inventory semantics

Receives add; sells subtract and can go below zero; moves transfer; counts set observed values only when expectations still match.

Transport retry ≠ operation conflict10

10 · Client pseudocode

Keep local state and cursors crash-safe

recordOffline(op):
  local transaction:
    request = { opId: uuid(), deviceId, deviceSeq: nextDeviceSeq,
                baseSeq: lastAppliedSeq, op }
    outbox.append(request)
    nextDeviceSeq += 1
    applyOptimistically(op)

sync():
  pullUntilCaughtUp()
  for request in outbox ordered by deviceSeq:
    response = POST(request)
    if success: remove request from outbox
    if timeout: retry exact request
  pullUntilCaughtUp()

pullUntilCaughtUp():
  page = GET(after = lastAppliedSeq)
  local transaction:
    apply page.ops ordered by seq
    save inventory and page.nextAfter together
  if page.hasMore: repeat
Use a stable device ID per app installation and group. Keep one lastAppliedSeq per group, not one global cursor for the whole account.
Mobile owns durable retry state; server owns group ordering11
12

Review · the protocol in five statements

Keep these invariants in mind

  1. Persist before sending. An offline operation must survive process death.
  2. Retry identically. Keep the same opId, deviceSeq, and body after a timeout.
  3. Order per device. Push outbox operations serially in deviceSeq order.
  4. Order per group. Use server seq and the client’s lastAppliedSeq for pulls.
  5. Commit state and cursor together. The inventory projection and pull cursor form one local transaction.
Check your understanding

Two devices both send deviceSeq: 1. Is that a collision?

Answer

No. Device sequence is scoped to a device. The backend assigns distinct group sequences, such as 12 and 13.
